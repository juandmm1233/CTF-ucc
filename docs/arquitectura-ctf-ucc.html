Tipo de aplicacion

No es un producto de produccion. Es un CTF de aula: dos apps LAMP (Apache + PHP 8.2 + MariaDB) mas un marcador Flask + SQLite. El modelo de juego es Attack & Defend simultaneo: cada equipo opera y defiende su VM mientras ataca la del rival.

Como se conectan los servicios

En pruebas locales el archivo raiz docker-compose.yml publica los tres stacks en una sola maquina, unidos por la red ctf_local_net. En clase, cada carpeta (ctf1/, ctf2/, scoreboard/) corre en su propia VM.

SQLite persiste puntajes

El banner del dashboard de cada lab lee SCOREBOARD_URL. Ese enlace es HTTP hacia el tablero; las bases MariaDB de IDS y UWS no se replican entre si. Por eso el scoreboard debe existir una sola vez en la red de clase.

Drivers y conectores

En este proyecto “driver” aparece en tres capas: el driver de red de Docker, el driver de volumen, y los conectores de aplicacion (mysqli y sqlite3).

MariaDB no usa un driver publicado al host

El puerto 3306 queda en la red bridge interna. Desde el navegador no se llega a MySQL. PHP resuelve ctf1_db_ssh / ctf2_db_ssh (all-in-one) o db_ssh (compose por VM) via el DNS embebido de Docker.

Por que bridge y no overlay

driver: bridge es el driver de red por defecto de un Compose en una sola maquina. Crea un switch virtual, asigna IP a cada contenedor y publica puertos con iptables/NAT. Overlay se usaria en Swarm/Kubernetes multi-nodo; este lab no lo necesita. El volumen scoreboard_data usa el driver local del daemon Docker.

Clasificacion de la aplicacion

Lo que es

CTF Attack & Defend containerizado. Cada lab es una aplicacion web clasica (no SPA): PHP renderiza HTML en el servidor, sesion por cookie, MariaDB para usuarios y secretos. El scoreboard es una app Flask MVC minima (plantillas Jinja + POST de banderas).

Arquitectura de despliegue: tres Compose independientes, pensados para 1 VM por equipo mas 1 VM de instructor. El all-in-one replica eso en localhost para debug.

Lo que no es

No es microservicios de negocio, ni API gateway, ni cluster Swarm. No hay autenticacion fuerte en el tablero, ni rate limit de produccion, ni TLS. El codigo web esta disenado para ser vulnerable (SQLi, LFI, RCE, etc.) con fines de clase.

IDS y UWS son clones funcionales con distinta identidad visual y distinta imagen de sistema para el contenedor db+ssh (Ubuntu vs Debian+Supervisor).

Restart y persistencia

Todos los servicios usan restart: unless-stopped. El codigo PHP se monta por bind mount (./ctf1/servidor_web y ./ctf2/servidor_web), asi que un parche en el host se refleja sin rebuild. El scoreboard copia el codigo en la imagen y persiste solo SQLite. Las bases MariaDB viven en el filesystem del contenedor db_ssh: docker compose down -v las borra.
